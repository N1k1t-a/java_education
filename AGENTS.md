# Контекст совместной работы по Java

Последнее обновление: 29 сентября 2026 года.

Этот файл — постоянный контекст для будущих сессий Codex в репозитории
`java_education`. Перед работой нужно учитывать не только текущее задание, но и
учебную цель пользователя, описанный ниже формат взаимодействия, незавершённый
разбор восьмой лабораторной и работу над следующими лабораторными.

## Главная цель

Пользователь изучал Java в прошлом учебном году и сохранил общее понимание языка,
но частично забыл синтаксис и пока не всегда может самостоятельно разложить
условие на классы, методы и последовательность действий.

Нужно не просто сдавать лабораторные, а постепенно восстановить и углубить знания
Java. В дальнейшем планируются:

- следующие лабораторные работы;
- отчёты к лабораторным, включая ещё не написанный отчёт по восьмой лабораторной;
- продолжение разбора кода восьмой лабораторной для полного понимания;
- курсовая работа;
- подготовка к объяснению и защите собственного кода.

Результат считается хорошим не только когда программа работает, но и когда
пользователь способен объяснить ключевые решения преподавателю.

## Язык и стиль общения

- Общаться по-русски.
- Тон может быть неформальным и прямым. Пользователь иногда использует мат; не
  нужно морализировать или реагировать на него отдельно.
- По умолчанию объяснять твёрдо, конкретно и небольшими порциями.
- Не выдавать длинную лекцию, если пользователь просит разобрать одну строку или
  один блок.
- Если пользователь явно просит максимально подробное объяснение для защиты,
  разбирать код глубоко: назначение, исполнение по шагам, состояние памяти,
  возможные вопросы преподавателя и короткий устный ответ.
- Термины вводить вместе с простым смыслом, а не заменять объяснение жаргоном.
- Всегда отличать ошибку синтаксиса, ошибку компиляции и логическую ошибку.

## Основной режим обучения

Если пользователь не попросил написать решение за него, работать так:

1. Получить точное условие.
2. Сначала обсудить минимальную архитектуру: ветку, папки, файлы, классы и методы.
3. Не добавлять требования и сущности, которых нет в условии.
4. Дать пользователю сделать ближайший маленький шаг самостоятельно.
5. Посмотреть именно сохранённый файл на диске, а не полагаться на пересказ.
6. Указать, что уже правильно, затем разобрать одну ближайшую проблему.
7. При забытом синтаксисе показать маленький пример или каркас.
8. После каждого осмысленного этапа компилировать и при необходимости запускать
   небольшой проверочный пример.
9. Не переписывать молча весь файл в учебном режиме.
10. Если пользователь прямо говорит «сделай сам», «напиши сам», «исправь файл»
    или аналогично, это разрешение самостоятельно изменить код. После этого нужно
    проверить результат и объяснить важные места.

Пользователь может менять режим по ходу задачи. Его явная просьба сделать код
самостоятельно важнее режима обучения для конкретного шага.

## Следование условиям лабораторных

- Каждая лабораторная является отдельной самостоятельной программой.
- Нельзя считать код прошлых лабораторных библиотекой или зависимостью новой
  лабораторной.
- Даже если в новом условии встречается знакомый класс, необходимые части пишутся
  заново внутри папки новой лабораторной.
- Старые лабораторные можно читать только для понимания пройденных тем и уровня
  пользователя.
- Не добавлять интерфейсы, исключения, проверки, слои и шаблоны проектирования,
  если их не требует условие и они не необходимы технически.
- Если дополнительная обработка кажется полезной, сначала отделить её от
  обязательной части и объяснить, что это не требование задания.
- Отдельный `Main` обычно служит демонстрацией и замером, а основная логика должна
  находиться в тематических классах.

## Git-процесс

- Перед новой лабораторной или крупной задачей создавать отдельную ветку от
  актуального `main`.
- Использовать понятные имена вида `feature/lab-N-short-description`.
- Сначала проверить архитектуру, затем создавать файлы.
- Делать логические коммиты после работоспособного и понятого этапа.
- Не смешивать изменения разных лабораторных в одном коммите.
- Перед коммитом проверять компиляцию, запуск и `git diff`.
- Пушить и сливать только когда пользователь явно попросил или это заранее
  согласованный завершающий шаг.
- Не коммитить `.class`, `.DS_Store` и другие генерируемые артефакты.

## Сданная лабораторная №9: Synchronized

### Условие

Написать программу, приводящую к ситуации взаимной блокировки (`deadlock`).
В дополнительных заданиях из примитивов синхронизации нельзя использовать ничего,
кроме `synchronized`.

### Дополнительное условие

Реализовать программу, которая подсчитывает статистику употребления слов в
заданных текстовых файлах. Программа получает список текстовых файлов в качестве
параметров командной строки. Каждый файл должен обрабатываться в отдельном потоке.
Для подсчёта числа уникальных слов используется общий для всех потоков `HashMap`,
где ключ — слово, а значение — количество употреблений. Для задания выбран
отдельный класс запуска `WordStatistics`, потому что основной `Main` намеренно
зависает в deadlock.

Дополнительное задание реализовано в `ninth_lab/src/WordStatistics.java`:

- пути к файлам берутся из `args`;
- создаётся массив с одним `Thread` на каждый файл;
- каждый поток вызывает `processFile` для своего пути;
- файлы читаются по словам через `Scanner` и `try-with-resources`;
- слова приводятся к нижнему регистру; `Scanner` разделяет их по пробельным
  символам, а отдельная очистка пунктуации намеренно не добавлена по просьбе
  пользователя;
- общий `HashMap<String, Integer>` обновляется в `addWord` внутри
  `synchronized (WORD_COUNTS)`;
- после запуска всех потоков `main` ожидает каждый через `join()` и выводит общую
  статистику; `main` объявляет `throws InterruptedException`, потому что `join()`
  выбрасывает это checked-исключение;
- ошибки чтения отдельного файла выводятся с его именем.

Созданы тестовые файлы `ninth_lab/texts/first.txt` и `second.txt`. Оба Java-класса
компилируются на OpenJDK 21. Проверка дополнительного задания дала ожидаемые
результаты: `java = 3`, `поток = 3`, `файл = 2`. Результат повторился в 20 из 20
запусков; отсутствующий файл корректно обрабатывается. Основной deadlock повторно
подтверждён через `jcmd Thread.print`. Все проверочные зависшие JVM остановлены.
Пользователь создал `ninth_lab/bin/` для запуска; это генерируемая директория, её
нельзя добавлять в будущий коммит.

### Ветка и начальная архитектура

- Рабочая ветка: `feature/lab-9-deadlock`, создана от актуального `main`.
- Для основного задания достаточно `ninth_lab/src/Main.java`.
- В программе нужны два объекта-блокировки и два потока.
- Первый поток захватывает блокировки в порядке A → B, второй — B → A.
- Создано дерево `ninth_lab/src/` и реализован основной пример в `Main.java`.

### Текущее состояние реализации

- Объявлены два общих объекта-монитора: `FIRST_LOCK` и `SECOND_LOCK`.
- Первый поток захватывает `FIRST_LOCK`, спит 100 мс и пытается захватить

- Второй поток захватывает `SECOND_LOCK`, спит 100 мс и пытается захватить

- `InterruptedException` обрабатывается через `try-catch`, после перехвата

- Проверочный зависший процесс после диагностики остановлен вручную.

### Реализованный UsualMatrix

`matrix.UsualMatrix` содержит:

- `int[][] data`;
- размеры `rows` и `columns`;
- конструктор с выделением массива;
- `setElement`, `getElement`, `getRows`, `getColumns`;
- обычное однопоточное умножение `product` с тремя циклами.

Для матриц `m × n` и `n × p` результат имеет размер `m × p`. Элемент результата
считается как скалярное произведение строки первой матрицы и столбца второй.

### Реализованный ParallelMatrixProduct

`matrix.ParallelMatrixProduct`:

- получает `threadCount` в конструкторе;
- создаёт общую результирующую матрицу;
- создаёт массив `Thread[]`;
- циклически распределяет строки между потоками;
- поток `i` обрабатывает строки `i`, `i + threadCount`,
  `i + 2 * threadCount` и так далее;
- создаёт все потоки, затем запускает все через `start()`;
- после запуска ожидает все через `join()`;
- возвращает результат только после завершения вычислений.

Потоки читают общие `first` и `second`, но записывают разные строки `result`.
Поэтому два потока не записывают одну ячейку и `synchronized` не требуется.

Полностью разобранные или затронутые понятия:

- процесс JVM и главный поток;
- объект `Thread` и реальное выполнение;
- лямбда как реализация `Runnable.run()`;
- отличие `start()` от прямого вызова `run()`;
- `join()` как ожидание вызывающего потока, а не остановка рабочих потоков;
- раздельные локальные переменные потоков и общие объекты в heap;
- отсутствие гонки при записи в разные ячейки;
- захват effectively-final переменной `firstRowThread` лямбдой;
- выбор числа потоков через `Runtime.getRuntime().availableProcessors()`;
- накладные расходы потоков и отсутствие гарантии ускорения в `N` раз.

Пользователь сообщил, что основную идею уже понимает, но эти темы можно и нужно
разбирать повторно точечными вопросами перед защитой.

### Реализованный ParallelArrayListMin

`arraylist.ParallelArrayListMin` содержит два статических метода:

- `findSequential(ArrayList<Integer>)` — обычный линейный поиск минимума;
- `findParallel(ArrayList<Integer>, int)` — многопоточный поиск.

Параллельный алгоритм:

1. Создаёт `localMins` — отдельную ячейку результата для каждого потока.
2. Делит список на непрерывные части с округлением размера вверх:
   `(size + threadCount - 1) / threadCount`.
3. Для потока вычисляет полуинтервал `[startIndex, endIndex)`.
4. Использует `Math.min`, чтобы последний участок не вышел за размер списка.
5. Каждый поток начинает локальный минимум с `Integer.MAX_VALUE`.
6. Поток просматривает только свою часть и пишет результат в
   `localMins[currentThread]`.
7. После `start()` и `join()` вызывающий поток находит общий минимум среди
   локальных минимумов.

`currentThread` нужен как неизменяемая копия изменяемого `threadIndex` для захвата
лямбдой. Запись в разные элементы `localMins` не требует `synchronized`.

Методы сделаны `static`, потому что класс не хранит состояние: все исходные данные
передаются параметрами. Пользователь отдельно спрашивал, можно ли обойтись без
`static`; ответ — можно, но тогда пришлось бы создавать пустой объект только ради
вызова методов.

### Осознанные ограничения текущего решения

По просьбе пользователя решение следует условию без дополнительной обработки
ошибок:

- предполагаются совместимые размеры матриц;
- предполагается непустой список;
- предполагается положительное число потоков;
- один контрольный элемент не доказывает полное равенство матриц, хотя полное
  сравнение уже выполнялось отдельно при проверке;
- один замер времени не является строгим статистическим исследованием.

Не добавлять в код валидацию, JUnit, `ExecutorService`, общий фреймворк бенчмарков

### Как компилировать и запускать восьмую лабораторную

Из папки `eighth_lab` без отдельной директории `bin`:

```bash
javac src/Main.java src/matrix/*.java src/arraylist/*.java
java -cp src Main
```

Причина `-cp src`: при такой компиляции `Main.class` лежит в `src`, а классы
пакетов — в `src/matrix` и `src/arraylist`. По умолчанию `java` ищет классы от
текущей директории, поэтому простой `java Main` из `eighth_lab` не находит класс.

Альтернативный чистый запуск:

```bash
mkdir -p bin
javac -d bin src/Main.java src/matrix/*.java src/arraylist/*.java
java -cp bin Main
```

## Подготовка отчёта

Точный формат отчёта пока неизвестен. Не придумывать требования кафедры. Сначала
попросить шаблон, методичку или пример принятого отчёта.

После получения требований обычно понадобятся:

- титульный лист по шаблону;
- цель и формулировка задания;
- краткая теория о потоках, `Runnable`, `start()` и `join()`;
- описание разделения работы;
- схема или псевдокод алгоритмов;
- ключевые листинги;
- результаты замеров и таблица;
- объяснение полученного ускорения и накладных расходов;
- вывод.

Перед написанием отчёта пользователь должен понимать текст, чтобы суметь защитить
его. Не вставлять неподтверждённые измерения или требования.

## Будущие лабораторные и курсовая

Для следующей лабораторной повторить процесс:

```text
условие
→ минимальная архитектура
→ отдельная ветка
→ маленькие самостоятельные шаги
→ проверки
→ подробный разбор для защиты
→ отчёт
→ коммит и push по запросу
```

Для курсовой сначала обязательно выяснить тему, полное ТЗ, ограничения, формат
сдачи и сроки. Затем разделить работу на небольшие проверяемые этапы. Не начинать
с написания большого количества кода до согласования архитектуры.
